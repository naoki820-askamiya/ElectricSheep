# 車載デバイス ⇄ サーバー WebSocket 仕様

Raspberry Pi（車載デバイス）とサーバーの間の取り決めです。
`src/types/api.ts` と同じく、**ここがチームのつなぎ目**になります。
変更するときは必ずフロント（ゆうすけ）・バックエンド（よしたか）・LLM（なおき）に共有してください。

対応する型定義: `src/types/ws.ts`
Pi 側の実装: `pi/passen_ws.py`

---

## なぜ WebSocket なのか

音声を扱うため、HTTP のリクエスト／レスポンスでは足りません。

- 発話は**いつ終わるか分からない**ので、録りながら送りたい
- 返事の音声も**先頭から順に再生**したい（全部届くまで待つと不自然になる）
- サーバー側から「今から喋ります」と**押しかける**必要がある

なお Next.js の Route Handler では WebSocket は動きません（接続が応答生成時に閉じられるため）。
サーバーは `/api/chat` とは**別プロセス**として立ててください。

---

## 接続

```
ws://<host>:<port>/ws?userId=<ユーザーID>
```

Pi は起動時に1本つなぎ、**そのまま繋ぎっぱなし**にします。
切れた場合、Pi は 1s → 2s → 4s → 8s（上限）で再接続を試みます。

---

## フレームの使い分け

| 種類 | 中身 |
|---|---|
| テキストフレーム | JSON の制御メッセージ。必ず `type` を持つ |
| バイナリフレーム | 音声データそのもの。ヘッダは付けない |

バイナリの解釈は、テキストメッセージで開始した**現在の音声状態**が決めます。
`wake` または `speech_start` から `end` までは「ユーザーの声」、
`audio_start` から `audio_end` までは「返事の音声」です。音声中に
`transcript`、`reply`、`location_request` が挟まっても音声状態は変わりません。

---

## 音声フォーマット

**Pi → サーバー（ユーザーの声）**

```
PCM signed 16-bit little-endian / 16000 Hz / モノラル / ヘッダ無し
1フレーム = 1280サンプル = 2560バイト = 80ms
```

16kHz なのは、ウェイクワード検出（openWakeWord）と音声認識の双方が
この周波数を前提にしているためです。Pi 側で変換済みのものを流します。

**サーバー → Pi（返事の音声）**

`audio_start` で宣言してください。Pi は2通りに対応します。

| encoding | 扱い |
|---|---|
| `pcm_s16le` | 届いた順にそのまま再生（遅延が小さい。こちらを推奨） |
| `wav` | 全部受け取ってから再生。VOICEVOX の出力をそのまま流す場合はこちら |

`pcm_s16le` の場合は `sampleRate` と `channels` を必ず入れてください。

## Pi → サーバー

### `hello`

接続直後に1回だけ送ります。

```json
{
  "type": "hello",
  "userId": "pi-demo",
  "device": "raspberrypi-4",
  "audio": { "encoding": "pcm_s16le", "sampleRate": 16000, "channels": 1 }
}
```

### `wake`

待ち受け中にウェイクワードを検出した合図です。新しいGemini Live会話を開始し、
**この直後からバイナリが流れ始めます。** 同じ会話の2回目以降には使いません。

```json
{ "type": "wake", "score": 0.87, "at": "2026-09-08T12:34:56.789Z" }
```

### `speech_start`

サーバーから `listen` を受けた後、Piが次の発話を検出した合図です。
同じGemini Live会話を継続し、この直後からバイナリを送ります。

```json
{ "type": "speech_start" }
```

### （バイナリフレーム）

ユーザーの声。80ms ごとに届きます。

### `end`

発話が終わった合図です。

```json
{ "type": "end", "reason": "silence" }
```

| `reason` | いつ送るか |
|---|---|
| `silence` | 話し終わって 1.2 秒沈黙した。**通常の終わり方** |
| `no_speech` | 呼びかけただけで 5 秒間何も話さなかった |
| `timeout` | 話し始めてから 10 秒たった |

**「話し始めるまで」と「話し終わってから」は別々に測っています。**
人は呼びかけたあと少し考えるので、両方を同じ長さにすると
「えーと」の間に打ち切られ、本題が一切録れません（実測で発生しました）。

`no_speech` のときはサーバーがGeminiへ `activityEnd` を送らず、会話を閉じます。
Piには `conversation_ended` が返ります。

それ以外を受け取ったら、**溜めた音声を処理して返事を返してください。**

### `location_result`

`location_request` に対する測位成功応答です。`requestId` は要求と同じ値を返します。
これが無いと、遅れて届いた古い応答を新しい要求の答えと取り違えます。

Pi は起動中ずっと GPS を読んでキャッシュしていますが、**待ち受け中に位置を
送ることはありません。** 常時送信は通信量の無駄であり、プライバシー上も
説明しづらいためです。測位に数十秒かかるので常時読み、送信は要求時だけ、
という両立にしています。

```json
{
  "type": "location_result",
  "requestId": "abc123",
  "lat": 35.07040,
  "lng": 137.23241,
  "accuracy": 11.3,
  "measuredAt": "2026-09-09T10:07:57Z"
}
```

`accuracy` は水平誤差の推定値（メートル）です。NMEA は誤差そのものを持たないため、
HDOP から概算しています。実測では HDOP 1.13 のとき ±12m でした。

### `location_error`

測位できない場合も、サーバーをタイムアウトまで待たせず必ず返します。
無応答だとサーバーが数秒待ち、その間ユーザーは黙ったままのAIを見つめることになります。

```json
{
  "type": "location_error",
  "requestId": "abc123",
  "code": "NO_FIX",
  "message": "衛星が足りず測位できていません"
}
```

| `code` | 意味 |
|---|---|
| `NO_DEVICE` | GPSが挿さっていない、ポートを開けない、GPS無効で起動 |
| `NO_FIX` | 受信できているが衛星が足りない（**屋内では普通に起きます**） |
| `STALE` | 測位はしたが古すぎる（トンネルに入った直後など） |
| `INTERNAL` | 想定外の失敗 |
| `NOT_IMPLEMENTED` | GPS実装前の暫定コード。**現在は送られません** |

実機で確認した値や NMEA の読み方は [gps-notes.md](gps-notes.md) にあります。

### `ping`

30秒ごと。接続維持の確認です。サーバーは `pong` を返してください。

## サーバー → Pi

### `ready`

`hello` への応答。これが来るまで Pi は `wake` を送りません。

```json
{ "type": "ready", "sessionId": "abc123" }
```

### `transcript`

聞き取り結果。**任意ですが、あると開発が楽になります。**
Pi の画面（ログ）に出して、認識のズレを目で追えるようにします。

```json
{ "type": "transcript", "text": "海が見たいな", "final": true }
```

### `reply`

AI の返事。`src/types/api.ts` の `ChatResponse` と同じ形です。

```json
{
  "type": "reply",
  "text": "海ですか。いいですね。どちらの海でしょう。",
  "suggestedPlace": {
    "id": "suggest-1",
    "name": "内海海水浴場",
    "location": { "lat": 34.7727, "lng": 136.8836 }
  }
}
```

`suggestedPlace` は行き先を提案したときだけ入れてください。雑談なら省略か `null` です。

### `audio_start` →（バイナリ）→ `audio_end`

読み上げ音声です。低遅延で再生を始めるため、`reply` より先に `audio_start` と
バイナリが届く場合があります。Piは音声区間中に届いた `reply` も処理します。

```json
{ "type": "audio_start", "encoding": "pcm_s16le", "sampleRate": 24000, "channels": 1 }
```

```json
{ "type": "audio_end" }
```

**`audio_end` は必ず送ってください。** Pi はこれを受け取るまで再生を終えられず、
次のメッセージへ進めません。

### `location_request`

Geminiの場所登録ツールが現在地を必要としたときに送ります。Piは同じ `requestId` で
`location_result` または `location_error` を必ず返します。

```json
{ "type": "location_request", "requestId": "abc123" }
```

### `listen`

返答後も同じGemini Live会話を続け、次のユーザー発話を待つ指示です。
Piは音声を外へ送らずローカルで発話開始を待ち、検出後に `speech_start` を送ります。

```json
{ "type": "listen", "timeoutSeconds": 180 }
```

### `conversation_ended`

Gemini Live会話を閉じ、ウェイクワード待ち受けへ戻る指示です。

```json
{ "type": "conversation_ended", "reason": "idle_timeout" }
```

`reason` は `user_requested` / `idle_timeout` / `no_speech` / `error`。

### `error`

```json
{ "type": "error", "code": "STT_FAILED", "message": "音声を認識できませんでした" }
```

Pi は内容をログに出し、**待ち受けに戻ります。** 接続は切りません。

### `pong`

```json
{ "type": "pong" }
```

### `location_request`

現在地が必要になったときに送ります。Gemini が場所の記録を判断したときなどです。

```json
{ "type": "location_request", "requestId": "abc123" }
```

Pi は `location_result` か `location_error` を返します。**どちらかは必ず返ります。**

## 会話の流れ

```
Pi                                     サーバー
──────────────────────────────────────────────────────
接続
  ├── hello ─────────────────────────►
  ◄────────────────────────── ready ──┤

（待ち受け。ウェイクワード検出のみ。音声は送らない）

「パッセンジャー」を検出（初回だけ）
  ├── wake ──────────────────────────►
  ├── バイナリ（80msごと）───────────►   溜める
  ├── バイナリ ──────────────────────►
  ├── end ───────────────────────────►
                                        音声認識 → LLM → 音声合成
  ◄────────────────────── transcript ─┤
  ◄───────────────────── audio_start ─┤
  ◄──────────────────────── バイナリ ─┤   再生開始
  ◄─────────────────────────── reply ─┤   音声区間中でも処理
  ◄───────────────────── audio_end ───┤
  ◄────────────────────────── listen ─┤

次の発話をローカルで検出
  ├── speech_start ───────────────────►
  ├── バイナリ（80msごと）───────────►
  ├── end ───────────────────────────►
                                      同じGemini Live会話で応答

会話終了
  ◄─────────────── conversation_ended ┤
ウェイクワード待ち受けへ戻る
```

## 決めておきたい点

**待ち受け中は音声を送りません。**
常時ストリーミングすると通信量が無駄で、プライバシー上も説明しづらくなります。
ウェイクワード検出は Pi 側で完結しており、**呼ばれるまでマイクの音は Pi の外に出ません。**

**割り込みは未対応です。**
再生中の Pi はマイクの入力を捨てています。ハウリングを避けるための割り切りで、
「AIが喋っている最中に遮る」ことは現状できません。
必要になったらエコーキャンセル付きのデバイスを用意するか、`cancel` メッセージを足します。

**再接続時、会話の文脈は失われます。**
履歴の保持はサーバー側の責任とします。Pi は `userId` しか持ちません。
