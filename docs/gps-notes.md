# GPS 実機メモ（実装前に読んでください）

`仕様書.pdf`（USB GPS・オンデマンド位置情報連携）を実装する人向けの、**実機で確認した事実**をまとめたものです。仕様の代わりではなく、仕様通りに作るための前提条件です。

計測日: 2026-09-09 / 確認者: ゆうすけ / 機材: Raspberry Pi 4 + VK-162

---

## いちばん重要な注意：`gpsd` と競合します

Pi には**すでに `gpsd` がインストール済み**です（動作確認のために入れました）。

`gpsd` はシリアルポートを占有します。`gps_reader.py` が `pyserial` で `/dev/ttyACM0` を直接開く設計なら、**両方は同時に動きません。** 「データが出てこない」の原因はほぼこれです。

**停止だけでは足りません。** `gpsd.socket` は「誰かが繋いだ瞬間に起動する」
仕組みなので、止めてもすぐ復活します。`mask` で起動そのものを禁止してください。

```bash
sudo systemctl mask gpsd.socket gpsd.service
sudo pkill -x gpsd
systemctl is-active gpsd.socket gpsd.service    # inactive が2行出れば成功
```

### gpsd は受信機の設定を書き換えます

実機で起きた事象です。**`gpsd` を止めたあとも NMEA が流れてこなくなりました。**

```
1回目（gpsd導入前）  GGA / GSA / GSV / GLL が1秒ごとに流れる
gpsd を動かす
2回目（gpsd停止後）  何も流れない
USB を抜き差し       TXT と RMC は流れるが GGA が無い
```

`gpsd` は u-blox へ UBX コマンドを送り、出力する文の種類を変更します。
**u-blox は設定をバックアップ電源付きメモリに保持するため、USBを抜き差ししても
元に戻りません。**

`gps_reader.py` は GGA が無ければ RMC から位置を取るようにしてあります。
ただし RMC には衛星数と HDOP が無いため、`accuracy` は返せません。

単体実行を `Ctrl+C` で終えると、受け取った文の一覧が出ます。

```
--- 受け取った NMEA 文 ---
  $GPRMC: 30回
  $GPVTG: 30回

  GGA が届いていません。受信機の設定で無効化されています。
```

GGA を戻したい場合は、UBX の CFG-MSG を送るか、受信機を工場出荷時に戻す
必要があります。**位置だけ必要なら RMC で足ります。**

---

実装前にどちらかを選んでください。

| 方式 | 内容 |
|---|---|
| **A. pyserial で直接読む**（仕様書の方式） | `gpsd` を止める。`sudo systemctl disable --now gpsd.socket gpsd.service` |
| B. `gpsd` 経由で読む | `gpspipe -w` の JSON か `gps` パッケージを使う。再接続や複数プロセスからの参照は `gpsd` が面倒を見てくれる |

仕様書は A を前提に書かれているので、**A なら `gpsd` の無効化を README とセットアップ手順に必ず入れてください。** 忘れると本番で動きません。

確認コマンド:

```bash
systemctl is-active gpsd.socket gpsd.service
sudo fuser -v /dev/ttyACM0        # 誰が掴んでいるか
```

## デバイス

| | |
|---|---|
| 製品 | VK-162（G-Mouse 型 USB GPS） |
| チップ | u-blox 7（`UBX-G70xx`、ROM CORE 1.00 / 2012-06-27） |
| プロトコル | NMEA 0183、PROTVER 14.00 |
| ポート | `/dev/ttyACM0`（USB CDC ACM。**ドライバ不要**） |
| ボーレート | 9600 bps |
| 測位系 | GPS + Galileo + SBAS。**QZSS は見えるが使われていない** |
| 更新レート | 1Hz |

`/dev/serial/by-id/` にも生えます。**挿し直しで `ttyACM0` の番号がずれることがある**ので、仕様書の優先順位（`by-id` を先に見る）は妥当です。

## 実測値

```
コールドスタート   26秒で 3D FIX（屋内・窓際）
ホットスタート     約1秒（RTCクリスタル内蔵）
見えた衛星         17個 / 使用 7個
SNR               18〜26 dB
水平誤差(EPX/EPY)  ±11.6 / ±12.4 m
HDOP              1.13
```

**実用精度は ±12〜20m** と考えてください。「どの道を通ったか」「どの施設に寄ったか」には十分ですが、番地の特定はできません。

### 屋内でも測位できましたが、余裕はありません

最初に机の上で試したときは**衛星1個・未測位**でした。窓際に移してから 17個見えました。

SNR 18〜26 は良好な屋外（35〜45 dB）に比べてかなり低く、**衛星が3つ落ちれば測位が外れます。** 車内はさらに条件が悪くなるので、実車での再計測が必要です。

パーサーを書くときのテストデータに使ってください。

### 起動直後（未測位）

```
$GPTXT,01,01,02,u-blox ag - www.u-blox.com*50
$GPTXT,01,01,02,HW  UBX-G70xx   00070000 *77
$GPTXT,01,01,02,PROTVER 14.00*1E
$GPTXT,01,01,02,ANTSTATUS=OK*3B
$GPRMC,,V,,,,,,,,,,N*53
$GPGGA,,,,,,0,00,99.99,,,,,,*48
$GPGSA,A,1,,,,,,,,,,,,,99.99,99.99,99.99*30
$GPGSV,1,1,01,16,,,30*7C

```

**未測位でも文章は流れ続けます。** 位置のフィールドが空になるだけです。
これは実装上ありがたい性質で、**屋内でも「受信機が生きているか」だけは確認できます。**

## パースすべき文章

最低限これだけ見れば足ります。

### `$GPGGA` — 位置と測位状態

```
$GPGGA,041523.00,3504.2241,N,13713.9445,E,1,08,1.02,32.3,M,...
       │         │         │ │          │ │ │
       │         │         │ │          │ │ └ 使用衛星数
       │         │         │ │          │ └ 測位品質 0=未測位 1=単独測位 2=DGPS
       │         │         │ │          └ 東経
       │         │         │ └ 経度 dddmm.mmmm
       │         │         └ 北緯
       │         └ 緯度 ddmm.mmmm
       └ UTC 時刻
```

**フィールド6（測位品質）が `0` なら座標を使ってはいけません。** 空文字が入っているだけのこともあります。

**緯度経度は「度分」形式です。** `3504.2241` は 35度4.2241分 であって 35.042241度ではありません。

```python
def to_degrees(value: str, hemisphere: str) -> float:
    """ddmm.mmmm / dddmm.mmmm を10進度に直す"""
    point = value.index(".")
    deg = int(value[: point - 2])
    minutes = float(value[point - 2 :])
    result = deg + minutes / 60
    return -result if hemisphere in ("S", "W") else result
```

ここを間違えると**日本のはずが北緯35度の全然違う場所**になります。ありがちな事故です。

### `$GPRMC` — 有効/無効フラグ

```
$GPRMC,041523.00,A,3504.2241,N,...
                 │
                 └ A=有効 V=無効
```

`V` のときは座標が空か、古い値です。

### `$GPGSA` / `$GPGSV` — 品質の判断に使う（任意）

`GPGSA` のフィールド2が `1`=未測位 / `2`=2D / `3`=3D です。
`GPGSV` は見えている衛星と SNR。**デバッグ時にしか要りません。**

## 実装上の落とし穴

### 静止中でも速度が出ます

```
Speed  0.83 km/h
Climb  5.76 m/min
```

止めた状態での実測です。GPS の宿命で、座標が数メートル揺れ続けます。

**「停車した」「ここに寄った」を `speed > 0` で判定してはいけません。** 3km/h 程度を閾値にしないと、駐車中もずっと移動中になります。同じ理由で、座標の微小変化を「移動」として記録すると、動いていないのに軌跡が増え続けます。

### 桁を残しても精度は上がりません

`35.07040123` と8桁出ますが、実際の誤差は ±12m です。

```
小数点以下5桁 ≒ 1m
小数点以下8桁 ≒ 1mm
```

**保存時は5桁に丸めることを勧めます。** 精度は落ちませんし、「1mm単位で個人の位置を記録している」という誤解も避けられます。

### 屋内では測位できないことがあります

デモ会場が屋内なら、**GPS は動かない前提で設計してください。** フロントエンドには擬似GPS（`NEXT_PUBLIC_USE_MOCK_GPS`）があります。サーバー側も、座標が来なかったときに会話が止まらないようにする必要があります。

一度測位すればホットスタート1秒なので、**会場に入る前に屋外で掴ませておく**運用は有効です。

### 電源断に注意

車のシガーソケットから給電する場合、エンジン始動時に電圧が落ちて Pi が落ちることがあります。GPS の問題ではありませんが、**同時に起きると原因の切り分けが難しくなります。**

## 通信仕様との対応

現在の [websocket-protocol.md](websocket-protocol.md) は、サーバーから要求されたときだけ
Piが位置情報を返す方式に統一されています。

**1. `location_request`（サーバー → Pi）**

```json
{ "type": "location_request", "requestId": "abc123" }
```

**2. `location_result`（Pi → サーバー、測位成功）**

```json
{
  "type": "location_result",
  "requestId": "abc123",
  "lat": 35.07040,
  "lng": 137.23241,
  "accuracy": 12.4,
  "measuredAt": "2026-09-09T10:07:57Z"
}
```

`requestId` を返すのは、**要求と応答を対応づけるため**です。無いと、遅れて届いた古い応答を新しい要求の答えと取り違えます。

**測位できていないときも必ず返してください。** 無応答だとサーバーがタイムアウトを待つことになります。

**3. `location_error`（Pi → サーバー、測位失敗）**

```json
{
  "type": "location_error",
  "requestId": "abc123",
  "code": "NO_FIX",
  "message": "測位できていません"
}
```

想定するエラー: `NOT_IMPLEMENTED`（GPS連携前）/ `NO_FIX`（衛星不足）/
`NO_DEVICE`（GPS未接続）/ `STALE`（キャッシュが古い）/ `INTERNAL`（その他）

`pyserial` で直接読む場合。

pyserial      # シリアルポートの読み取り

`pynmea2` は便利ですが、必要な文章は2種類だけなので**自前で書いても50行程度**です。依存を増やしたくなければ不要です。

## 動作確認の手順

実装した人が最初に確認すべき順序です。**上から順にやれば、どこで詰まったか特定できます。**

```bash
# 1. 認識されているか
lsusb | grep -i u-blox
ls -l /dev/serial/by-id/ /dev/ttyACM*

# 2. gpsd が邪魔していないか
sudo fuser -v /dev/ttyACM0

# 3. 生データが流れるか（屋内でも流れる）
timeout 5 cat /dev/ttyACM0

# 4. 測位できるか（屋外・空が見える場所）
timeout 60 cat /dev/ttyACM0 | grep --line-buffered GPGGA
```

4番で `$GPGGA,...,1,08,...` のように**測位品質が 1 以上**になれば成功です。
